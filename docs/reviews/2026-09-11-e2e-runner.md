## Issues left unfixed (advisory)

- [high] security/injection: The tools (bash, read, write) are rooted at targetDir via cwd but this is not a chroot/container/egress boundary. Bash can cd / read any file and reach network; the stated credential boundary depends on denied bash grants for untrusted roles. Document plainly in ARCHITECTURE.md/README.md that cwd is a starting directory only and bash grants full FS+network access; defer real sandboxing (seccomp/container/egress deny) as a follow-up.

- [medium] security/data_exposure: The credential boundary silently depends on the harness process cwd differing from targetDir. If an operator launches ad-coder with cwd inside or equal to targetDir, Bun auto-loads targetDir/.env into process.env at startup and the models built from that env now carry the target's credentials — the boundary collapses without any code reading targetDir/.env. Document and enforce (in CLI wiring) that credentials must be resolved before/independently of targetDir; refuse or warn when resolved absTargetDir equals or contains process.cwd(). Track this as part of the runner deployment checklist.

- [low] security/input_validation: FileLedgerSink enforces O_NOFOLLOW only on the final file component. Pre-planted symlinks at `<targetDir>/.ad-coder` or `<targetDir>/.ad-coder/ledger` redirect ledger writes outside targetDir. Resolve the real path of the ledger directory and verify it is contained within absTargetDir with no symlinked components before opening (e.g. fs.realpathSync on the parent and prefix check), or create the `.ad-coder/ledger` chain with per-component symlink checks. At minimum refuse to write when an intermediate component is a symlink.

- [low] security/input_validation: The default ledger path uses the caller-supplied params.runId before it is validated against RUN_ID_PATTERN. Traversal is currently blocked implicitly by Ledger constructor synchronously throwing, but the runner could return a path computed from an unvalidated runId. Validate params.runId against RUN_ID_PATTERN before constructing the FileLedgerSink path, so a malformed runId cannot form a filesystem path; do not depend on Ledger constructor throw ordering.

- [low] security/data_exposure: RunRoleResult carries the full settled OperationResultRecord including assistant message content and request detail. The CLI's stdout discipline only protects the workflow's own return value; a workflow that returns the runRole result verbatim writes full prompt/response content to stdout, bypassing that discipline. Document that RunRoleResult.result carries request detail and must not be returned/logged wholesale. Consider returning a narrowed result (status + minimal fields) by default, or a JSDoc warning on RunRoleResult.

- [info] security/input_validation: resolveScriptPath in cli.ts refuses symlinks; resolveTargetDir only checks exists-and-is-directory. Decide and document targetDir's trust stance: if it should match resolveScriptPath, refuse a symlinked targetDir (or fs.realpathSync it and report the resolved path). If symlinks are intentionally allowed, state that in the JSDoc so the difference is deliberate, not accidental.
