# Architecture

## What this is

ad-coder is a small, explicit agent scaffold built on `@earendil-works/pi-agent-core`. It provides four primitives: a `Role` is a validated preset over harness options that pins a model, system prompt, and tool allow-list; a `Ledger` attributes token usage and cost to roles and runs as JSONL; the runner (`runRole`/`createRoleRunner`) constructs a live harness rooted at an explicit target directory and drives one turn; and a workflow module is a plain object the CLI loads and executes. It builds on pi-agent-core rather than pi-coding-agent, and disables Pi's own compaction so the context strategy stays under ad-coder's control.

## Stack

- **Runtime:** Bun (TypeScript, no build step)
- **Agent framework:** @earendil-works/pi-agent-core@0.85.1
- **AI provider SDK:** @earendil-works/pi-ai@0.85.1
- **Database/state:** none; Ledger writes JSONL to disk
- **Testing:** bun:test, no network

## Components

- **Role (src/role.ts):** Validated preset containing name, provider, modelId, systemPrompt, activeToolNames array, cacheRetention setting, and a `contextBudget`. Exports `defineRole(role, model)` — which now takes the target `Model` and validates the budget against its real `contextWindow` — and `toHarnessOptions()` to construct pi-agent-core's `AgentHarnessOptions` with compaction disabled and system prompt passed verbatim. `toHarnessOptions()` still emits `compaction: { enabled: false, reserveTokens: 0, keepRecentTokens: 0 }` and never mirrors the role's real budget numbers into Pi's settings.
- **Context (src/context/):** ad-coder's owned context-window strategy, mirroring the ledger's injected-seam layout. `budget.ts` defines `ContextBudget` ({maxTokens, reserveTokens, keepRecentTokens}), `validateContextBudget()` (the boundary check `defineRole` runs), and the typed `ContextBudgetError`. `compactor.ts` defines the `Summarizer` seam, the exported `SUMMARIZATION_PROMPT`, `selectRecentTail()`, and `ContextCompactor` — a `transform_context` hook (id `ad-coder/context-compactor`) that, when a turn exceeds `maxTokens - reserveTokens`, summarizes the evicted head through the injected summarizer and returns `[summary, ...recent tail]`. Like the Ledger it does not throw inside the hook: a summarizer failure increments `compactionFailures` and warns once to stderr with numbers only. `preflight.ts` exports `assertTurnFitsBudget(role, messages, model)`, a pre-flight (not a hook) that throws `ContextBudgetError` when the irreducible tail plus reserve exceeds the ceiling; it shares `selectRecentTail` with the compactor so both agree on what cannot be evicted.
- **Capabilities (src/capabilities/):** Pure functions over a hand-buildable pi-ai `Model` (no network, no keys). `deriveCapabilities(model)` returns a `ModelCapabilities` descriptor: `costMode` (`per-token` when any cost field is nonzero; else `local` when the baseUrl host is loopback/private — parsed with `new URL().hostname` inside try/catch, unparseable falling through to non-local — or the provider matches `/lmstudio|vllm|local/i`; else `prepaid`), `cacheControllable`, `contextWindow`, cache read/write unit costs, and `outInRatio`. Two metrics computed from what the ledger already writes: `cacheEfficiency(usage) = cacheRead / (cacheRead + input)` (both-zero guarded to 0) and `breakEvenReads(model)`, which returns the numeric threshold `cacheWrite / (input - cacheRead)` or one of two ordered sentinels — `"always"` when cacheWrite is 0, `"degenerate"` when input <= cacheRead. `reconcileRoleWithModel(role, model)` returns a `ReconcileWarning[]` (never throws): one `inert-cache-retention` warning when a role sets a non-`none` cacheRetention on a model that cannot honor it, empty otherwise. Role is imported type-only; the module modifies no shared runtime. The empirical declared-vs-observed layer is a deferred follow-up.
- **Ledger (src/ledger/):** Registers an after_response hook on a harness and appends one JSONL record per turn carrying that response's own token and cost numbers, plus role/step/run attribution. It records the per-response usage directly (pi-agent-core adds each row's usage to session totals at `harness/session/in-memory-storage-state.js:67`, which is only correct if the row is already per-response) and holds no per-stream counters. Records carry identifiers and numbers only — never prompt text, message content, or headers.
- **UsageDeltaTracker (src/ledger/usage.ts):** Pure function `diffUsage()` that subtracts consecutive Usage snapshots to derive per-turn deltas, plus a per-stream baseline map. Retained and exported for a genuinely cumulative source such as `message_update` (where `pi-ai` emits absolute values into one mutable `output.usage`), and deliberately not used on the after_response path (which is per-response). Handles optional fields (cacheWrite1h, reasoning) by conditional spread, and clamps negative deltas to 0 with an anomaly flag rather than emitting negative costs. `usageAmounts()` in the same file copies one reading into the ledger's shape through an explicit allow-list, building a fresh `cost` object so caller mutations do not alter already-written records.
- **Quality gates (src/gates/):** Data-declared mechanical checks run BEFORE an LLM review round because they cost no tokens ("gates over prompts"). `types.ts` defines the `QualityGate` config ({name, kind: 'format'|'lint'|'typecheck'|'size', command?, autofix?, maxLinesPerFile?}) — commands are config, not hardcoded, so the module is language- and provider-agnostic — plus the injected `CommandExecutor` seam `(argv, cwd) => Promise<ExecResult>`, mirroring the ledger's sink so tests hand it a fake and nothing shells out. `runner.ts` defines `GateRunner`, which over supplied file paths runs any declared `autofix` argv first then the `command` argv (a gate passes iff the check's exitCode is 0), captures TRUNCATED stdout+stderr (fixed char cap plus a marker so a verbose or hostile tool cannot flood the report), and includes an in-process `size` gate that reads files only to count lines and fails a file exceeding `maxLinesPerFile`, naming the file and its exact count. The aggregate `GateReport` is fail-loud: `passed` is the AND of all results and each result names its verdict, so a caller can feed the failures back as the next turn's input. The runner only ever builds argv arrays (never a shell string) and never interpolates file contents into a command. No real spawn executor ships here and gates are NOT yet wired into ad-coder's own build — a deliberate separate follow-up.
- **Runner (src/runner/):** The end-to-end glue that constructs a live harness and drives one turn. `errors.ts` defines the typed `RunnerError` (a `code` discriminant — `missing`/`not_found`/`not_a_directory`/`invalid_run_id`/`unsafe_ledger_dir` — plus the offending path, numbers-and-paths only), `resolveTargetDir()` (rejects empty input, `realpath`-resolves and requires an existing directory), `assertRunId()` (validates the run id against the same file-name pattern the Ledger uses, BEFORE any path is built from it), and `assertLedgerDirWithinTarget()` (refuses a symlinked `.ad-coder`/`.ad-coder/ledger` component so the ledger cannot be redirected out of targetDir). `runner.ts` exports `runRole(params)`: it resolves targetDir, builds `NodeExecutionEnv({ cwd: absTargetDir })` and the `[bash, read, write, edit]` tools rooted there, projects the Role via `toHarnessOptions`, constructs the Ledger over a `FileLedgerSink` at `<targetDir>/.ad-coder/ledger/<runId>.jsonl` (the sink seam — NOT the `filePath` option, which is confined to the harness cwd), optionally attaches a `ContextCompactor`, creates the harness via `AgentHarness.create`, and drives `harness.lane('main').prompt(...)` to a settled `OperationResultRecord`, closing the harness and ledger in a `finally`. `role-runner.ts` exports the `RoleRunner` interface and `createRoleRunner(config)`, which binds targetDir + models (+ optional summarizer/session) and delegates each call to `runRole`. The runner never reads `process.env` or `<targetDir>/.env` — provider auth arrives only through the caller-configured models.
- **Workflow module (src/workflow.ts):** Plain object contract: `{ name: string; run(ctx: WorkflowContext): Promise<unknown> }`. CLI loads a .ts file by path, validates the default export, and executes `run()`. `WorkflowContext` carries `runId` and `ledger` always, and an OPTIONAL `runRole?: RoleRunner` present only when the CLI was given `--target-dir`; the additive field leaves `isWorkflowModule` (which validates the module shape, not the context) untouched.
- **CLI (src/cli.ts):** Entrypoint `ad-coder run <script.ts> [--target-dir <dir>]` that validates the path (requires a regular file, owned by current user, not world-writable), generates a runId via `crypto.randomUUID()`, instantiates a Ledger, invokes the workflow's run function, prints the result as JSON, and exits 0 on success or 2 on usage error. When `--target-dir` is supplied it builds a `RoleRunner` (credentials from `builtinModels()` — the CLI's OWN environment, never `<targetDir>/.env`) and passes it as `ctx.runRole`; it warns when the process cwd is inside targetDir, because Bun auto-loads a `.env` there into `process.env` and that would fold the target's credentials into the environment.

## How they connect

A workflow module is loaded by the CLI, which constructs a Ledger with a generated runId and passes both to `run()`. A workflow that drives a role calls `ctx.runRole` (present when the CLI was launched with `--target-dir`): the runner instantiates the harness via `AgentHarness.create`, roots the `[bash, read, write, edit]` tools at targetDir through `NodeExecutionEnv`, projects the Role to `AgentHarnessOptions` via `toHarnessOptions()`, and drives one `lane.prompt` turn. The Ledger's `attach()` method registers an after_response hook that fires on every turn, records that response's own Usage (already per-response from the hook's settled message), and appends one JSONL record per turn to `<targetDir>/.ad-coder/ledger/<runId>.jsonl` — under the agent's target directory, never the harness cwd. The workflow returns a value, which the CLI prints as JSON.

## Key decisions

- **No Pi compaction; ad-coder owns the context strategy:** Pi provides built-in message summarization via CompactionSettings, but its prompt is a hardcoded constant. We disable it (`compaction: { enabled: false, ... }`) and implement the strategy in `src/context/`: a per-role `ContextBudget`, a `transform_context` compactor that summarizes the evicted head through ad-coder's own `SUMMARIZATION_PROMPT`, and an `assertTurnFitsBudget` pre-flight for the irreducible case. The real budget numbers stay out of Pi's disabled CompactionSettings.
- **Caller-supplied Model, no catalog lookup:** `defineRole` and `assertTurnFitsBudget` read `contextWindow` off a `Model` object the caller passes in, rather than resolving the model id against Pi's builtin catalog. ad-coder targets local and custom OpenAI-compatible endpoints (LM Studio, vLLM, self-hosted qwen) that are absent from that catalog; a catalog lookup would reject their ids and never see their real window. `resolveRoleModel` remains only as the builtin-catalog convenience for models that are in it.
- **The compactor counts failures instead of throwing:** A `transform_context` handler's throw is caught and discarded by the harness aggregate, so a thrown summarizer error would vanish and the turn would silently go out uncompacted anyway. The compactor mirrors `Ledger.droppedRecords`: it increments `compactionFailures`, warns once to stderr with numbers only, and passes the messages through untransformed. The refusal path — where nothing can be evicted — is the exported pre-flight function, not the hook.
- **cacheControllable is api-OR-format, not format alone:** Whether a model honors `cacheRetention` is `model.api === "anthropic-messages" || model.compat.cacheControlFormat === "anthropic"`. The format-only rule (`cacheControlFormat === "anthropic"`) is a false negative on native Anthropic: `claude-fable-5` is `api: "anthropic-messages"` with NO `compat.cacheControlFormat`, yet honors cacheRetention through `getCacheControl` (pi-ai anthropic-messages.js:29); the format path (openai-completions.js:808) only covers openai-completions models emulating Anthropic markers. The read uses a `"cacheControlFormat" in model.compat` guard because on `Model<Api>` `compat` is a union of all four compat types and the field lives only on `OpenAICompletionsCompat` (types.d.ts:516) — a bare `compat?.cacheControlFormat` does not type-check under strict. The local/prepaid split is a best-effort, overridable baseUrl+provider heuristic; per-token is reliable because it reads price, not host.
- **Ledger reads provider cost, never recomputes it:** A record's cost is the provider's own reported `Usage.cost` block, copied field by field in a fresh object so a caller's later mutations do not alter an already-written record, never recalculated from tokens times a rate, so the audit trail cannot drift from provider billing.
- **Role is a preset, not runtime-mutable:** It is shaped to stay additive (the `contextBudget` field landed this way; promptLimit, handoffPolicy could follow without breaking the harness Options type). It is the minimal validated set that closes the gap between a provider model name and pi-agent-core's required harness options.
- **activeToolNames is emitted unconditionally:** An undefined field in AgentHarnessOptions grants all registered tools; an empty array is a valid deny-all. We emit activeToolNames always, never conditionally, so a role's intent is explicit.
- **Per-stream deltas, not per-role:** When `UsageDeltaTracker` is applied to a cumulative source it keys by `${runId}:${lane}` (stream identity), not by role, because two roles sharing a lane share the cumulative counter — keying by role would produce inflated first-turn deltas for each. The ledger write path records the reading directly with no diffing at all.
- **Filesystem sandboxing:** runId is validated against `/^[A-Za-z0-9_-]{1,64}$/`, ledger paths are resolved and required to stay inside the base directory, and record files are opened with O_NOFOLLOW to block symlink attacks.
- **Runner: harness-dir ≠ target-dir, and the tools are not confined:** The runner takes a REQUIRED explicit `targetDir` (resolved to an absolute, existing directory) that is the agent's working directory: tools start there and the ledger lands under it, never at the harness's own cwd. Credentials arrive ONLY through the caller-configured `models`/`model`; the runner never reads `process.env` or `<targetDir>/.env`. That boundary also depends on the harness cwd being distinct from targetDir — Bun auto-loads a `.env` from the process cwd into `process.env`, so the CLI warns when cwd is inside targetDir. `NodeExecutionEnv({ cwd })` sets only the shell's STARTING directory: it is NOT a chroot, container, or egress boundary, so a bash turn can `cd /`, read any file the harness user can read, and reach the network. targetDir CONTENT is untrusted; the real gate is the Role's `activeToolNames` (deny-all or a read/write-scoped set for a role that ingests untrusted input — never bash without an out-of-process sandbox). Real sandboxing (seccomp/container/egress deny) is tracked as a follow-up. The ledger placement uses the Ledger `sink` seam (a `FileLedgerSink` under targetDir), not the `filePath` option (confined to the harness-cwd base dir); the runner refuses a symlinked `.ad-coder`/`.ad-coder/ledger` component so a pre-planted symlink under an untrusted targetDir cannot redirect the write.
