# Architecture

## What this is

ad-coder is a small, explicit agent scaffold built on `@earendil-works/pi-agent-core`. It provides four primitives: a `Role` is a validated preset over harness options that pins a model, system prompt, and tool allow-list; a `Ledger` attributes token usage and cost to roles and runs as JSONL; the runner (`runRole`/`createRoleRunner`) constructs a live harness rooted at an explicit target directory and drives one turn; and a workflow module is a plain object the CLI loads and executes. It builds on pi-agent-core rather than pi-coding-agent, and disables Pi's own compaction so the context strategy stays under ad-coder's control.

## Stack

- **Runtime:** Bun (TypeScript, no build step)
- **Agent framework:** @earendil-works/pi-agent-core@0.85.1
- **AI provider SDK:** @earendil-works/pi-ai@0.85.1
- **Database/state:** none; Ledger writes JSONL to disk
- **Testing:** bun:test, no network

## Components

- **Role (src/role.ts):** Validated preset containing name, provider, modelId, systemPrompt, an OPTIONAL activeToolNames array, cacheRetention setting, and a `contextBudget`. Exports `defineRole(role, model)` — which now takes the target `Model` and validates the budget against its real `contextWindow` — and `toHarnessOptions()` to construct pi-agent-core's `AgentHarnessOptions` with compaction disabled and system prompt passed verbatim. `activeToolNames` is default-open: ABSENT means "every registered tool" (the harness reads `activeToolNames ?? tools.map((t) => t.name)`, so `toHarnessOptions` OMITS the key entirely when the role leaves it unset), a present `[]` is a deny-all emitted verbatim, and a present array is the exact set — `defineRole` allows undefined but still rejects a present non-array, and `toHarnessOptions` branches on `!== undefined` (never on `.length`) so a `[]` deny-all can never silently become full access. `toHarnessOptions()` still emits `compaction: { enabled: false, reserveTokens: 0, keepRecentTokens: 0 }` and never mirrors the role's real budget numbers into Pi's settings.
- **Context (src/context/):** ad-coder's owned context-window strategy, mirroring the ledger's injected-seam layout. `budget.ts` defines `ContextBudget` ({maxTokens, reserveTokens, keepRecentTokens}), `validateContextBudget()` (the boundary check `defineRole` runs), and the typed `ContextBudgetError`. `compactor.ts` defines the `Summarizer` seam, the exported `SUMMARIZATION_PROMPT`, `selectRecentTail()`, and `ContextCompactor` — a `transform_context` hook (id `ad-coder/context-compactor`) that, when a turn exceeds `maxTokens - reserveTokens`, summarizes the evicted head through the injected summarizer and returns `[summary, ...recent tail]`. Like the Ledger it does not throw inside the hook: a summarizer failure increments `compactionFailures` and warns once to stderr with numbers only. `preflight.ts` exports `assertTurnFitsBudget(role, messages, model)`, a pre-flight (not a hook) that throws `ContextBudgetError` when the irreducible tail plus reserve exceeds the ceiling; it shares `selectRecentTail` with the compactor so both agree on what cannot be evicted.
- **Capabilities (src/capabilities/):** Pure functions over a hand-buildable pi-ai `Model` (no network, no keys). `deriveCapabilities(model)` returns a `ModelCapabilities` descriptor: `costMode` (`per-token` when any cost field is nonzero; else `local` when the baseUrl host is loopback/private — parsed with `new URL().hostname` inside try/catch, unparseable falling through to non-local — or the provider matches `/lmstudio|vllm|local/i`; else `prepaid`), `cacheControllable`, `contextWindow`, cache read/write unit costs, and `outInRatio`. Two metrics computed from what the ledger already writes: `cacheEfficiency(usage) = cacheRead / (cacheRead + input)` (both-zero guarded to 0) and `breakEvenReads(model)`, which returns the numeric threshold `cacheWrite / (input - cacheRead)` or one of two ordered sentinels — `"always"` when cacheWrite is 0, `"degenerate"` when input <= cacheRead. `reconcileRoleWithModel(role, model)` returns a `ReconcileWarning[]` (never throws): one `inert-cache-retention` warning when a role sets a non-`none` cacheRetention on a model that cannot honor it, empty otherwise. Role is imported type-only; the module modifies no shared runtime. The empirical declared-vs-observed layer is a deferred follow-up.
- **Ledger (src/ledger/):** Registers an after_response hook on a harness and appends one JSONL record per turn carrying that response's own token and cost numbers, plus role/step/run attribution. It records the per-response usage directly (pi-agent-core adds each row's usage to session totals at `harness/session/in-memory-storage-state.js:67`, which is only correct if the row is already per-response) and holds no per-stream counters. Each record also carries an OPTIONAL `toolCalls` map (tool name → requested count) derived from the SAME settled message via the pure `toolCallCounts()` helper, omitted when the response requested no tools. Honest granularity: this is what the model REQUESTED in that one response (per-response, matching usage), NOT whether a call executed or returned `isError` — execution outcome needs the separate `after_tool` hook and is a documented follow-on. Records carry identifiers and numbers only — never prompt text, message content, tool arguments, tool output, or headers.
- **UsageDeltaTracker (src/ledger/usage.ts):** Pure function `diffUsage()` that subtracts consecutive Usage snapshots to derive per-turn deltas, plus a per-stream baseline map. Retained and exported for a genuinely cumulative source such as `message_update` (where `pi-ai` emits absolute values into one mutable `output.usage`), and deliberately not used on the after_response path (which is per-response). Handles optional fields (cacheWrite1h, reasoning) by conditional spread, and clamps negative deltas to 0 with an anomaly flag rather than emitting negative costs. `usageAmounts()` in the same file copies one reading into the ledger's shape through an explicit allow-list, building a fresh `cost` object so caller mutations do not alter already-written records.
- **Quality gates (src/gates/):** Data-declared mechanical checks run BEFORE an LLM review round because they cost no tokens ("gates over prompts"). `types.ts` defines the `QualityGate` config ({name, kind: 'format'|'lint'|'typecheck'|'size', command?, autofix?, maxLinesPerFile?}) — commands are config, not hardcoded, so the module is language- and provider-agnostic — plus the injected `CommandExecutor` seam `(argv, cwd) => Promise<ExecResult>`, mirroring the ledger's sink so tests hand it a fake and nothing shells out. `runner.ts` defines `GateRunner`, which over supplied file paths runs any declared `autofix` argv first then the `command` argv (a gate passes iff the check's exitCode is 0), captures TRUNCATED stdout+stderr (fixed char cap plus a marker so a verbose or hostile tool cannot flood the report), and includes an in-process `size` gate that reads files only to count lines and fails a file exceeding `maxLinesPerFile`, naming the file and its exact count. The aggregate `GateReport` is fail-loud: `passed` is the AND of all results and each result names its verdict, so a caller can feed the failures back as the next turn's input. The runner only ever builds argv arrays (never a shell string) and never interpolates file contents into a command. No real spawn executor ships here and gates are NOT yet wired into ad-coder's own build — a deliberate separate follow-up.
- **Runner (src/runner/):** The end-to-end glue that constructs a live harness and drives one turn. `errors.ts` defines the typed `RunnerError` (a `code` discriminant — `missing`/`not_found`/`not_a_directory`/`invalid_run_id`/`unsafe_ledger_dir`/`tool_name_collision` — plus the offending path/name, numbers-and-paths only), `resolveTargetDir()` (rejects empty input, `realpath`-resolves and requires an existing directory), `assertRunId()` (validates the run id against the same file-name pattern the Ledger uses, BEFORE any path is built from it), `assertLedgerDirWithinTarget()` (refuses a symlinked `.ad-coder`/`.ad-coder/ledger` component so the ledger cannot be redirected out of targetDir), and `assertUniqueToolNames()` (rejects a duplicate name across the COMBINED built-in + custom tool set BEFORE harness construction, so a collision surfaces as a typed error instead of the harness's raw `TypeError`). `tool.ts` is ad-coder's own tool surface: the `Tool` type alias (`= AgentHarnessTool<ExecutionToolContext>`) and the `defineTool` identity helper (parallel to `defineRole`), so callers author custom tools against ad-coder's boundary rather than a raw pi type. `runner.ts` exports `runRole(params)`: it resolves targetDir, builds `NodeExecutionEnv({ cwd: absTargetDir })` and the built-in `[bash, read, write, edit]` tools rooted there, then concatenates any caller-supplied `params.tools` (the OPTIONAL tool-injection seam) and runs `assertUniqueToolNames` on the combined set before projecting the Role via `toHarnessOptions`, constructs the Ledger over a `FileLedgerSink` at `<targetDir>/.ad-coder/ledger/<runId>.jsonl` (the sink seam — NOT the `filePath` option, which is confined to the harness cwd), optionally attaches a `ContextCompactor`, creates the harness via `AgentHarness.create`, and drives `harness.lane('main').prompt(...)` to a settled `OperationResultRecord`, closing the harness and ledger in a `finally`. The tools seam is ADDITIVE (custom tools EXTEND the built-ins; absent `tools` reproduces prior behavior byte-for-byte) and a name colliding with a built-in or another custom tool is REJECTED, never shadowed; `activeToolNames` filters the COMBINED set uniformly, so a role exposes a custom tool only by listing its name — a custom tool absent from a non-empty activeToolNames is filtered out exactly like a built-in. `role-runner.ts` exports the `RoleRunner` interface and `createRoleRunner(config)`, which binds targetDir + models (+ optional summarizer/session) and delegates each call to `runRole`, forwarding a per-call `opts.tools` (per-call, not bound — one RoleRunner drives multiple roles and only some need a custom tool). The runner never reads `process.env` or `<targetDir>/.env` — provider auth arrives only through the caller-configured models. The tool-injection seam is what the orchestration reviewer's `submit_verdict` tool-call verdict rides on, and it unblocks further per-role custom tools (e.g. a conversational orchestrator's run-pipeline / show-ledger tools).
- **Conversation (src/conversation/):** The multi-turn substrate the conversational orchestrator will sit on, built on the SAME runner seams WITHOUT editing `src/runner/` or `src/orchestration/pipeline.ts` (both stay byte-for-byte). `startConversation(config)` resolves targetDir, validates the runId, roots the built-in `[bash, read, write, edit]` tools (plus any injected `config.tools`, guarded by `assertUniqueToolNames`) at targetDir via `NodeExecutionEnv`, projects the Role through `toHarnessOptions`, and builds ONE harness over ONE session; it acquires the lane ONCE and attaches the `ContextCompactor` ONCE (attaching it per turn would compound `transform_context` handlers exactly as a per-turn ledger attach would compound rows). It returns a `ConversationSession` whose `step(userInput, opts?)` re-drives that same `lane.prompt` seam: pi retains history on the durable Session branch tip, so there is NO transcript replay. Each `step` builds a FRESH per-turn `Ledger` sharing the ONE sink, attaches its ledger + a `tool_end` events listener and unsubscribes BOTH in a `finally` on every turn (`hooks.on`/`events.on` have no dedup, so a leaked listener would duplicate the next turn's rows and tool calls — N turns therefore emit exactly N ledger rows), throws on a `suspended` record exactly as `runRole`, and narrows the settled `OperationResultRecord` to `{status, assistantText, toolCalls, droppedRecords}` (the full record never leaves `step`, matching the `RunRoleResult` security note). `assistantText` comes from a reimplemented `extractFinalText` (the pipeline's is private) — newest-first scan of `findEntries({type:'message', order:'desc'})` for the first assistant message, joining its `{type:'text'}` blocks, `''` when none. `step` NEVER calls `ledger.close()` (it would close the SHARED sink); only `close()` closes the harness and then the sink, exactly once. Credentials come only from `config.models`/`config.model`; the ledger path is guarded by `assertLedgerDirWithinTarget` — the same boundaries as `runRole`, which stays the single-turn primitive.
- **Orchestration (src/orchestration/):** Composes the single-turn runner into a plan → (code⇄review) pipeline WITHOUT touching `src/runner/`. `types.ts` defines the `Verdict` contract (`status: 'approved' | 'changes_requested'`, `issues: {severity, what}[]`, `summary`), the `Plan` contract (`complexity: 'trivial' | 'medium' | 'complex'`, `securitySurface: 'none' | 'low' | 'elevated'`, `summary`) with its `Complexity` and `SecuritySurface` literal sets, the `PipelineConfig` (whose `roles` gained an OPTIONAL `security?` role)/`PipelineResult` (the latter carrying OPTIONAL `complexity?` and `securitySurface?` signals)/`RoleSpec`/`RoundRecord` shapes, and the typed `OrchestrationError` (a `code` discriminant — `missing_verdict`/`malformed_verdict`/`malformed_plan`/`invalid_max_rounds`/`empty_task` — plus a `detail` string carrying the offending path or number only, mirroring `RunnerError`). `plan.ts` mirrors `verdict.ts` for the planner's untrusted-plan boundary: `SUBMIT_PLAN_TOOL_NAME`, `buildSubmitPlanTool(capture, detail)` (a `defineTool` tool whose TypeBox `parameters` schema is PERMISSIVE at the `complexity` and `securitySurface` leaves — `Type.String`, not a union of literals — so a malformed value reaches the validator instead of being bounced pre-execute, and whose `execute` runs `parsePlan` inside try/catch, storing the plan or the caught `OrchestrationError` into a per-turn `PlanCapture` holder rather than throwing), `parsePlan()` (a pure hand-written strict validator — `complexity` in the three literals, `securitySurface` in the three literals, `summary` a string — that throws `malformed_plan` on any deviation, never coercing or defaulting a bad `securitySurface`), and `formatPlannerInstruction()` (the fixed template telling the planner to CALL the tool). CRUCIAL soft/hard split: unlike the verdict, an ABSENT `submit_plan` call is NOT an error — it leaves `PipelineResult.complexity` undefined and the run proceeds on the free-text plan (there is deliberately NO `missing_plan`); only a MALFORMED submission is a hard `malformed_plan`. Complexity is a routing SIGNAL for a later follow-on; this unit makes it AVAILABLE but does NOT wire it into model selection. `verdict.ts` owns the untrusted-verdict boundary: `SUBMIT_VERDICT_TOOL_NAME`, `buildSubmitVerdictTool(capture, detail)` (a `defineTool` tool whose TypeBox `parameters` schema is PERMISSIVE at the enum leaves — `status`/`severity` as `Type.String` — so a malformed value reaches the validator instead of being bounced by the harness's pre-execute schema check, and whose `execute` runs `parseVerdict` inside try/catch, storing the verdict or the caught `OrchestrationError` into a per-round `VerdictCapture` holder rather than throwing, because the harness swallows an execute throw into an error tool-result), `parseVerdict()` (a pure hand-written strict validator — `status` in the two literals, `issues` an array of `{severity ∈ {blocker,major,minor}, what: string}`, `summary` a string — that throws `malformed_verdict` on any deviation, never `eval`, never trusting shape; it stays the authoritative gate), and `formatReviewerInstruction()` (the fixed template telling the reviewer to CALL the tool with the required shape, exported so pipeline and tests agree). No filesystem artifact is written or read. `pipeline.ts` exports `runPipeline(config)`: it validates `maxRounds >= 1` and a non-empty task, binds one `createRoleRunner({targetDir, models})`, runs the optional planner ONCE (`step: 'plan'`) — handing it a fresh `PlanCapture` + `buildSubmitPlanTool` and, after the turn, re-throwing a captured `malformed_plan`, recording a captured plan's `complexity`/`securitySurface` onto the result, or leaving them undefined on an empty holder — then runs the CONDITIONAL Security phase (`step: 'security'`) IFF the plan's `securitySurface` is `elevated` AND a `security` role is configured, driving that read/bash-only role with the task + plan summary + a fixed OWASP threat-model instruction and capturing its final text as `securityNotes` (elevated with no security role skips with one content-free stderr note and proceeds; the surface is still reported on the result); it then threads `securityNotes` as hard requirements into the coder's ROUND-1 prompt and EVERY reviewer prompt (as DATA, exactly like a `VerdictIssue.what` — never into a shell/SQL/path sink; round 2+ carry unmet mitigations forward via the reviewer's issues, so it is not re-injected each coder round) — then loops the coder (`step: 'code:N'`) and reviewer (`step: 'review:N'`) to `maxRounds`; on `changes_requested` the reviewer's issues become the coder's next prompt, on `approved` it returns `{approved: true, rounds}`, and exhausting the cap returns `{approved: false}` (never thrown). Each role-run gets its OWN fresh `MemorySessionRepo` session (roles must not share history/systemPrompt); the run's final assistant text is read via `extractFinalText`, which scans `findEntries({type:'message', order:'desc'})` newest-first for the last assistant message and joins its `{type:'text'}` blocks (runRole closes the session facade it was handed, so the pipeline reopens a fresh readable facade from the same repo — the MemoryStorage behind it survives). The verdict is a `submit_verdict` TOOL CALL: each reviewer round builds a fresh `VerdictCapture` holder plus `buildSubmitVerdictTool` and passes it through the reviewer turn's `tools`, then reads the holder — a captured error throws `malformed_verdict`, an empty holder throws `missing_verdict`, a captured verdict drives approve/changes_requested (last-wins on a repeated call). No JSON artifact is written or read. Two non-obvious harness facts shape the capture-holder bridge: the harness validates tool args against the schema BEFORE execute (so the schema stays permissive at the enum leaves), and it swallows an execute throw into an error tool-result (so the tool records `parseVerdict`'s error into the holder rather than throwing, and the pipeline re-throws it after the turn). The reviewer role must list `submit_verdict` in its `activeToolNames`, since `activeToolNames` gates the combined tool set. `session.ts` re-expresses that whole plan → [security] → code ⇄ review graph as an explicit STEPPED ENGINE so the step graph lives exactly once: `createWorkflowSession(config)` validates up front (`empty_task`/`invalid_max_rounds`), builds the routing/runner/`pickModel` once, and owns `pickModel`/`runTurn`/`extractFinalText` and the prompt composers (moved out of `pipeline.ts`); its `step(state)` runs the ONE pending role turn (recording runId/verdict/ledger step, throwing `missing_verdict`/`malformed_verdict`/`malformed_plan` at the same points as before) and returns `{state, result, transitions}` WITHOUT committing a transition, while the PURE `applyTransition(state, chosen)` yields the next state and `autoDriver` picks the single `isDefault` edge. A driver chooses `advance`/`rework`/`stop`: the default edges reproduce the old rules exactly (plan→security only when elevated AND a security role, else plan→code; security→code; code→review; approved→stop(true); changes_requested with rounds left→next code round, else stop(false)). Honoring `docs/contracts/config.md`, the transition policy is a SETTING not a constant — an OPTIONAL `WorkflowDefaults` (`onChangesRequested`, `autoAdvance`, plus `maxRounds`/`defaultComplexity`) each defaulting to today's behavior. `pipeline.ts`'s `runPipeline` is now the thin AUTO-DRIVER over this engine (`step` → `applyTransition(state, autoDriver(transitions))` until done, then `toPipelineResult(state)`), byte-for-byte its prior signature, errors, ledger labels and runId ordering; the engine is the substrate a human-stepped UI or the conversational orchestrator drives with its own driver. `transition-guard.ts` now OWNS the driver-boundary guard (`DriveError`/`DriveErrorCode`/`assertTransitionOffered`), relocated DOWN from `src/cli/drive.ts` (which re-exports it byte-for-byte) so a core module — the orchestrator — can depend on the guard without pulling in a CLI front; both drivers share the one implementation. `orchestrator.ts` is the THIRD driver of that stepped engine, alongside `runPipeline`'s auto-driver and the human `drive` CLI, and it is where a MODEL (not just the operator) decides when to run the pipeline, with what task, and which transition to take. It is a headless core plus a thin tool front in one file. `createOrchestrator(deps)` is the core: `deps` carry a per-task `buildConfig(task) => PipelineConfig` factory and a shared `MemoryLedgerSink`, and the core spreads that sink over every config it builds so cost is always read from the one sink. It exposes `runPipeline(task)` (autonomously auto-drives a whole run, returning `{result, perStep, totalCost}`), `beginStepping`/`stepOnce`/`chooseTransition`/`showCost` (the same engine one step at a time), and `isStepping`. Per-step cost is attributed by ledger-record POSITION — snapshot `sink.records().length` before and after each `session.step` and sum the delta — NOT a `record.runId` join, for the same reason `costForRange` sums by position (a record's `runId` is the harness op id, not the step runId). HARD INVARIANT: `chooseTransition(kind)` treats the model-supplied `kind` as untrusted — it resolves it via `find` against the engine-authored offered `AvailableTransition[]`, throws `DriveError('transition_not_offered', kind)` (carrying ONLY the kind) when absent, and passes the resolved edge through `assertTransitionOffered` before `applyTransition`; it NEVER fabricates or accepts a model-supplied `toPhase`/`toRound`, so a run cannot be driven off its own graph (e.g. jumped to `done`). `buildOrchestratorTools(core)` is the thin front: four `defineTool` tools (`run_pipeline` {task}, `run_step` {task?}, `choose_transition` {kind, rationale?}, `show_cost` {}) whose handlers marshal args→core→text ONLY and catch every throw through `safeErrorText`, which projects a house error's `code`+`detail` (never `String(error)`/stack/message, which can carry paths) so a `RegistryError('missing_credential')` or a `DriveError` surfaces safely into the transcript. The schemas expose ONLY those fields — never `targetDir`, a path, or a provider/registry override — so the trust boundary (fixed targetDir, engine-authored transitions) cannot be widened from a tool call. `startOrchestrator(config)` assembles the conversational front: it wires `resolvePipelineConfig` (the per-task `buildConfig` factory and the SOLE credential surface — keys resolve only through its injected `env`, never `targetDir/.env`), `resolvePrompt('orchestrator')`, and `startConversation` with the four tools, all sharing ONE `MemoryLedgerSink`. `run_pipeline` is code-execution-capable within `targetDir` (a starting cwd, not a sandbox — the pipeline's coder holds bash/write/edit there); the model authors only the `task` string, threaded as prompt DATA via `PipelineConfig.task`, never into a shell/path/URL sink. Typed `OrchestratorError` (`no_active_session`/`awaiting_transition`/`no_pending_transition`) guards the manual-stepping call ordering.
- **Registry (src/registry/):** The bottom two layers of the config model as plain data, resolved into a live pi `Models`. A LEAF module — it imports only `@earendil-works/pi-ai` (and its `api/*.lazy` + `providers/*` subpaths), no sibling `src/` runtime. `types.ts` defines the plain shapes: a `ProviderConfig` (`id`, `api: ApiKind`, `baseUrl`, a `CredentialSource` = an env-var NAME or `oauth`, `models`) and its `ModelConfig`s (`name` stable lookup key + `modelId` + `contextWindow`/`maxTokens`/`reasoning`/`cost`, exactly what `deriveCapabilities` consumes, plus an optional per-model `api` override for dual-api providers and an inert `compat` pass-through). `errors.ts` is the typed `RegistryError` (a `code` discriminant — `invalid_config`/`duplicate_provider`/`duplicate_model`/`unsupported_api`/`missing_credential`/`unknown_model` — plus a `detail` carrying an identifier/name ONLY, never a value). `validate.ts` is `parseRegistryConfig`, a pure hand-written fail-loud validator mirroring `parsePlan`: it rejects duplicate provider ids and model names, unsupported apis, empty env-var names, non-finite costs, and — a hard security requirement — a `baseUrl` that is not an absolute **https** URL by exact-scheme equality or that embeds userinfo. TRUST BOUNDARY: the config author is TRUSTED; the https check is scheme-hardening (no cleartext key transmission), NOT a host-level exfiltration control, and the module doc says so — if config ever originates from a less-trusted source, host-level controls must be added. `presets.ts` is the FIVE preset builders (`deepseek`, `openrouter`, custom `openaiCompatible`, custom `anthropicCompatible`, `openaiCodex`) — no separate native-OpenAI/native-Anthropic preset; those are reached via the custom presets. `resolve.ts` is `resolveRegistry(config, { env })`: it ALWAYS re-validates, reads each env-var credential through the injectable `env` accessor (default `process.env`, the only credential source — never a target-dir dotenv) with a fail-loud `missing_credential` preflight (because `envApiKeyAuth.resolve` returns undefined rather than throwing on a missing key), builds a pi `Models` via `createModels` whose `AuthContext.env` routes to that same accessor and whose `fileExists` returns `false` (so pi cannot fall back to an ambient file), registers each env-var provider via `createProvider` (single or `model.api`-keyed mixed-API form) and DELEGATES any `oauth` provider to the shipped `openaiCodexProvider()` factory (ignoring its declared baseUrl — codex is OAuth-only, no token handling here), and returns `{ models, getModel(name), lookup(name) }` where lookup resolves the pi `Model<Api>` by stable name or throws `unknown_model`. Wired into nothing yet — consumption by the role/profile layers is a follow-on.
- **Profiles (src/profiles/):** The top two layers of the config model, completing the four-layer chain **provider → model → profile → override**. It composes ABOVE a resolved registry: `resolveProfile(profile, registry, role, complexity, override?)` resolves a `(role, complexity)` routing cell — or a per-spawn `SpawnOverride` that takes precedence — to a registry model NAME, then through `registry.getModel` to a live pi `Model<Api>`, returning a `ResolvedSelection` with the model plus an ADVISORY `{ maxOutput, cacheRetention }`. Those hints are produced but have NO sink in this unit; the wiring follow-on maps `maxOutput` onto pi `StreamOptions.maxTokens` and `cacheRetention` onto the role's stream options. `types.ts` defines `ProfileRole` (`planner|coder|reviewer|security|recorder` — `recorder` is a forward-looking routing target `runPipeline` does not consume, kept in sync with `PipelineConfig.roles` keys by hand, no compile-time link), `ProfileEntry`, `Profile`, `SpawnOverride`, and `ResolvedSelection` (`CacheRetention` reused verbatim from pi-ai, never redefined). `errors.ts` is the typed `ProfileError` (a `code` discriminant — `invalid_config`/`duplicate_entry`/`unknown_role`/`invalid_complexity`/`missing_mapping`/`unknown_model` — plus a names-only `detail`; `unknown_model` is intentionally shared with `RegistryError`'s code and distinguished by error CLASS). `validate.ts` is `parseProfile`, a pure hand-written fail-loud validator mirroring `parseRegistryConfig`/`parsePlan`: a non-empty `entries` array, known role/complexity literals, a non-empty model name, positive-finite optional `maxOutput`, valid optional `cacheRetention`, and seen-Set duplicate detection on the composite `role:complexity` key. `resolveProfile` CATCHES a `RegistryError('unknown_model')` from the lookup and rethrows `ProfileError('unknown_model', name)` so a `RegistryError` never escapes and the layer presents ONE typed surface; a missing `(role, complexity)` cell throws `ProfileError('missing_mapping', 'role:complexity')`. `default-profile.ts` is `buildDefaultProfile({ strong, mid, cheap })`, a provider-agnostic builder taking registry NAMES (no hardcoded provider ids) that emits one entry per `(role x complexity)` pair (15 total): planner/security → strong, reviewer → mid, recorder → cheap, coder complexity-scaled (trivial→cheap, medium→mid, complex→strong). Now CONSUMED by `runPipeline` through the optional `PipelineConfig.routing`: complexity-aware per-role model selection is live (the planner routes on `defaultComplexity`; later roles on the planner's submitted tier). A `resolveProfile` config error (`missing_mapping`/`unknown_model`) propagates UNWRAPPED as its own `ProfileError`, distinct from the pipeline's `OrchestrationError` surface.
- **Workflow module (src/workflow.ts):** Plain object contract: `{ name: string; run(ctx: WorkflowContext): Promise<unknown> }`. CLI loads a .ts file by path, validates the default export, and executes `run()`. `WorkflowContext` carries `runId` and `ledger` always, and an OPTIONAL `runRole?: RoleRunner` present only when the CLI was given `--target-dir`; the additive field leaves `isWorkflowModule` (which validates the module shape, not the context) untouched.
- **CLI (src/cli.ts):** Three entrypoints: (1) `ad-coder run <script.ts> [--target-dir <dir>]` validates the path (requires a regular file, owned by current user, not world-writable), generates a runId via `crypto.randomUUID()`, instantiates a Ledger, invokes the workflow's run function, prints the result as JSON, and exits 0 on success or 2 on usage error. When `--target-dir` is supplied it builds a `RoleRunner` (credentials from `builtinModels()` — the CLI's OWN environment, never `<targetDir>/.env`) and passes it as `ctx.runRole`. (2) `ad-coder role <name> "<task>" --target-dir <dir> [options]` runs a single named role (planner|coder|reviewer|security) standalone on a task, resolving its model via `resolvePipelineConfig` with optional provider/model/maxRounds overrides. Extracts the final assistant text from the role's turn (via a local copy of the extract logic), sums per-run cost from the ledger, and prints text then cost to stdout. On an empty-text/zero-cost turn (indicating a provider auth failure or model returning nothing), writes a clear stderr warning before the stdout text/cost. (3) `ad-coder drive "<task>" --target-dir <dir> [--auto]` drives the stepped workflow engine (from `src/orchestration/session.ts`) one phase at a time via an interactive loop (`src/cli/drive.ts`): calls `resolvePipelineConfig` to build the config, creates a `WorkflowSession`, and loops `session.step()` yielding printed phase/runId/cost and a menu of available transitions (advance/rework/stop). In interactive mode (default) reads human choices via node:readline over injected stdin/stdout/stderr (testable without a TTY, scriptable via piped input); `--auto` swaps the human read for `autoDriver` so the path reproduces `runPipeline`'s autonomous behavior for scripting/CI. A driver-boundary guard validates that a chosen transition is one the step actually offered and throws a typed `DriveError` ('transition_not_offered') on mismatch — this is the guard the future orchestrator-driver relies on. All three paths warn when the process cwd is inside targetDir, because Bun auto-loads a `.env` there into `process.env` and that would fold the target's credentials into the environment.

- **CLI Config (src/cli/resolve-config.ts):** Environment-to-config resolver that builds a complete `PipelineConfig` from environment variables and command-line overrides. `resolvePipelineConfig(options)` selects a provider by env-var PRESENCE (precedence DEEPSEEK_API_KEY → OPENROUTER_API_KEY → codex-oauth fallback), builds a `ResolvedRegistry` from the matching preset (deepseek/openrouter/openai-codex), and routes strong/mid/cheap model names through `buildDefaultProfile` (each defaulting to the chosen preset's default model name, overridable via flags). Derives the context budget as a PERCENT of the smallest chosen tier model's `contextWindow` so one budget validates for all four roles. Builds planner/coder/reviewer/security Roles via `defineRole` from the BUILT-IN prompts and the real registered models, assembles `PipelineConfig` with `MemoryLedgerSink`, and threads the resolved models/profile/registry through the routing chain. Reads env-vars ONLY through an injectable accessor (default `process.env`), never directly, to enable testing with a fake env. Throws `RegistryError('missing_credential', <VAR>)` when a forced provider's key is absent.

- **CLI Drive (src/cli/drive.ts):** The testable core of the interactive drive subcommand, decoupled from the CLI's argument parsing and TTY. `driveWorkflow(params)` is the loop that drives a `WorkflowSession` to completion step by step: it takes `{ session, ledgerSink, auto, input, output, error }` (all streams are injectable, so a test piping scripted choices or a CI script reading a fifo can drive the loop without a real TTY), runs `session.step()` once per loop iteration, prints the resulting phase/runId/cost and available transitions to output, and on an empty-text/zero-cost turn writes a warning to error. When `auto` is false, reads human choices via node:readline over the input stream (rl.question for per-prompt awaiting, works with `Readable.from(string)` without blocking or hanging), mapping input by kind (case-insensitive) or index to an offered transition; empty input selects the marked default. When `auto` is true, calls `autoDriver(transitions)` to pick the default transition. Before applying a chosen transition, `assertTransitionOffered(chosen, transitions)` guards the boundary: it throws `DriveError('transition_not_offered', chosen.kind)` if the transition's `kind`+`toPhase`+`toRound` do not match one the step offered (the match is by value, not reference, because `autoDriver` and human mapping both pull from the offered array, but the future orchestrator-driver may hand a reconstructed transition). The pure `applyTransition` is never weakened — the guard belongs only in the driver boundary. `silentNoopWarning(text, cost)` exports the fixed stderr message for an empty-text/zero-cost turn (provider may need auth e.g. codex login, or the model returned nothing), returning the message string when `text.trim()==="" && cost===0`, else undefined. The guard itself (`DriveError`/`DriveErrorCode`/`assertTransitionOffered`) now LIVES in `src/orchestration/transition-guard.ts`; `drive.ts` imports `assertTransitionOffered` for its own loop and re-exports all three byte-for-byte, so `driveWorkflow` and every existing importer are unchanged while the orchestrator core can depend on the guard without this CLI front. Exports `silentNoopWarning`, the re-exported `DriveError`/`DriveErrorCode`, plus the main `driveWorkflow` function.

- **Prompts (src/prompts/):** A leaf boundary helper that turns a role's system prompt from an inline `fs.readFileSync` into a name reference. `resolvePrompt(name, opts?)` resolves a bare `name` to a verbatim UTF-8 string over a two-tier search path: a PROJECT prompt at `<projectDir>/.ad-coder/prompts/<name>.md` (when `projectDir` is given) OVERRIDES the built-in package prompt shipped at repo-root `prompts/<name>.md` (located package-relative via `import.meta.dir + "../../prompts"`, which survives a global install because the package ships source with siblings intact and has no `files` allow-list). The file is returned UNCHANGED — no trim, no normalize, no templating — because it is the cacheable verbatim cache prefix a role hands to `defineRole`; the resolver only maps name → verbatim string and never alters `Role.systemPrompt`'s meaning. `name` is validated against `/^[A-Za-z0-9_-]+$/` (non-empty, no dots/slashes/`..`) BEFORE any path is joined — the same validate-before-path-build discipline as `assertRunId` — so a traversal name throws `PromptError('invalid_name')` with an empty `pathsTried` before any fs access. `errors.ts` is the typed `PromptError` (a `code` discriminant — `invalid_name`/`not_found` — plus the offending `promptName` and the absolute `pathsTried`, names-and-paths only, NEVER file contents or the prompt body, since verbatim system-prompt bytes could hold sensitive instructions). A project override silently shadows the shipped prompt (the intended feature) — the `pathsTried` list in a `not_found` error is the only observability. TASK/user-prompt templating is explicitly OUT of scope, a documented follow-on.

## How they connect

A workflow module is loaded by the CLI, which constructs a Ledger with a generated runId and passes both to `run()`. A workflow that drives a role calls `ctx.runRole` (present when the CLI was launched with `--target-dir`): the runner instantiates the harness via `AgentHarness.create`, roots the `[bash, read, write, edit]` tools at targetDir through `NodeExecutionEnv`, projects the Role to `AgentHarnessOptions` via `toHarnessOptions()`, and drives one `lane.prompt` turn. The Ledger's `attach()` method registers an after_response hook that fires on every turn, records that response's own Usage (already per-response from the hook's settled message), and appends one JSONL record per turn to `<targetDir>/.ad-coder/ledger/<runId>.jsonl` — under the agent's target directory, never the harness cwd. The workflow returns a value, which the CLI prints as JSON.

**Config layers:** A four-layer model stacks provider → model → profile → override. The `Registry` resolves provider credentials and model metadata; the `Profiles` layer resolves a (role, complexity) routing cell — or a per-spawn `SpawnOverride` — to a named registry model, then to a live pi `Model<Api>`, yielding advisory {maxOutput, cacheRetention} hints. That chain is now CONSUMED by `runPipeline`: an OPTIONAL `PipelineConfig.routing` ({profile, registry, defaultComplexity?, overrides?}) drives per-role model selection off the planner-rated complexity — the planner (and any pre-complexity role) routes on `defaultComplexity` (default 'medium'), and every later role routes on the planner's submitted tier, else that same default. When `routing` is absent, selection is byte-for-byte the prior behavior: each `RoleSpec.model` over `config.models`. (The advisory {maxOutput, cacheRetention} hints still have no sink; only model selection is wired.)

`runPipeline` sits one level above the runner: it threads one shared `targetDir` through `createRoleRunner`, and each role hands its final assistant TEXT to the next role's prompt while the reviewer hands its structured VERDICT to the pipeline through a `submit_verdict` TOOL CALL. Each reviewer round builds a fresh `VerdictCapture` holder plus `buildSubmitVerdictTool`, passes the tool through the reviewer turn's `tools`, and reads the holder after the turn settles — a captured error throws `malformed_verdict`, an empty holder (the reviewer never called the tool) throws `missing_verdict`, and a captured verdict is strictly validated by `parseVerdict` inside the tool. A missing/malformed verdict is a hard `OrchestrationError`, a well-formed `changes_requested` is a legitimate non-approval. Nothing touches the filesystem for the verdict. Per-role/per-round cost separates cleanly because every run carries a distinct `step` (`plan`, `security`, `code:N`, `review:N`) plus `role.name`; passing one `ledgerSink` in the config makes the whole pipeline write a single readable ledger. Runs are strictly sequential, so that shared sink needs no concurrency handling.

## Key decisions

- **No Pi compaction; ad-coder owns the context strategy:** Pi provides built-in message summarization via CompactionSettings, but its prompt is a hardcoded constant. We disable it (`compaction: { enabled: false, ... }`) and implement the strategy in `src/context/`: a per-role `ContextBudget`, a `transform_context` compactor that summarizes the evicted head through ad-coder's own `SUMMARIZATION_PROMPT`, and an `assertTurnFitsBudget` pre-flight for the irreducible case. The real budget numbers stay out of Pi's disabled CompactionSettings.
- **Caller-supplied Model, no catalog lookup:** `defineRole` and `assertTurnFitsBudget` read `contextWindow` off a `Model` object the caller passes in, rather than resolving the model id against Pi's builtin catalog. ad-coder targets local and custom OpenAI-compatible endpoints (LM Studio, vLLM, self-hosted qwen) that are absent from that catalog; a catalog lookup would reject their ids and never see their real window. `resolveRoleModel` remains only as the builtin-catalog convenience for models that are in it.
- **The compactor counts failures instead of throwing:** A `transform_context` handler's throw is caught and discarded by the harness aggregate, so a thrown summarizer error would vanish and the turn would silently go out uncompacted anyway. The compactor mirrors `Ledger.droppedRecords`: it increments `compactionFailures`, warns once to stderr with numbers only, and passes the messages through untransformed. The refusal path — where nothing can be evicted — is the exported pre-flight function, not the hook.
- **cacheControllable is api-OR-format, not format alone:** Whether a model honors `cacheRetention` is `model.api === "anthropic-messages" || model.compat.cacheControlFormat === "anthropic"`. The format-only rule (`cacheControlFormat === "anthropic"`) is a false negative on native Anthropic: `claude-fable-5` is `api: "anthropic-messages"` with NO `compat.cacheControlFormat`, yet honors cacheRetention through `getCacheControl` (pi-ai anthropic-messages.js:29); the format path (openai-completions.js:808) only covers openai-completions models emulating Anthropic markers. The read uses a `"cacheControlFormat" in model.compat` guard because on `Model<Api>` `compat` is a union of all four compat types and the field lives only on `OpenAICompletionsCompat` (types.d.ts:516) — a bare `compat?.cacheControlFormat` does not type-check under strict. The local/prepaid split is a best-effort, overridable baseUrl+provider heuristic; per-token is reliable because it reads price, not host.
- **Ledger reads provider cost, never recomputes it:** A record's cost is the provider's own reported `Usage.cost` block, copied field by field in a fresh object so a caller's later mutations do not alter an already-written record, never recalculated from tokens times a rate, so the audit trail cannot drift from provider billing.
- **Role is a preset, not runtime-mutable:** It is shaped to stay additive (the `contextBudget` field landed this way; promptLimit, handoffPolicy could follow without breaking the harness Options type). It is the minimal validated set that closes the gap between a provider model name and pi-agent-core's required harness options.
- **activeToolNames is emitted unconditionally:** An undefined field in AgentHarnessOptions grants all registered tools; an empty array is a valid deny-all. We emit activeToolNames always, never conditionally, so a role's intent is explicit.
- **Per-stream deltas, not per-role:** When `UsageDeltaTracker` is applied to a cumulative source it keys by `${runId}:${lane}` (stream identity), not by role, because two roles sharing a lane share the cumulative counter — keying by role would produce inflated first-turn deltas for each. The ledger write path records the reading directly with no diffing at all.
- **Filesystem sandboxing:** runId is validated against `/^[A-Za-z0-9_-]{1,64}$/`, ledger paths are resolved and required to stay inside the base directory, and record files are opened with O_NOFOLLOW to block symlink attacks.
- **Runner: harness-dir ≠ target-dir, and the tools are not confined:** The runner takes a REQUIRED explicit `targetDir` (resolved to an absolute, existing directory) that is the agent's working directory: tools start there and the ledger lands under it, never at the harness's own cwd. Credentials arrive ONLY through the caller-configured `models`/`model`; the runner never reads `process.env` or `<targetDir>/.env`. That boundary also depends on the harness cwd being distinct from targetDir — Bun auto-loads a `.env` from the process cwd into `process.env`, so the CLI warns when cwd is inside targetDir. `NodeExecutionEnv({ cwd })` sets only the shell's STARTING directory: it is NOT a chroot, container, or egress boundary, so a bash turn can `cd /`, read any file the harness user can read, and reach the network. targetDir CONTENT is untrusted; the real gate is the Role's `activeToolNames` (deny-all or a read/write-scoped set for a role that ingests untrusted input — never bash without an out-of-process sandbox). Real sandboxing (seccomp/container/egress deny) is tracked as a follow-up. The ledger placement uses the Ledger `sink` seam (a `FileLedgerSink` under targetDir), not the `filePath` option (confined to the harness-cwd base dir); the runner refuses a symlinked `.ad-coder`/`.ad-coder/ledger` component so a pre-planted symlink under an untrusted targetDir cannot redirect the write.
- **Conversation: harness built once, history via the branch, not replay:** The multi-turn substrate builds ONE harness/session/lane and re-drives `lane.prompt` per `step`, because pi retains history on the durable Session branch tip — replaying a transcript each turn would be wasteful and wrong. Two things are per-turn and two are once-per-conversation, and getting the split wrong duplicates state: the Ledger and its `tool_end` listener are rebuilt and unsubscribed EVERY turn (`hooks.on`/`events.on` have no dedup, so a leaked listener double-counts the next turn), while the harness, the lane and the compactor are attached ONCE (a per-turn compactor attach would compound `transform_context` handlers the same way). The shared ledger sink is closed exactly once, in `close()` — never by the per-turn `ledger.close()`, which would break every later turn. This is deliberately a SEPARATE entry point from `runRole` (which stays the single-turn primitive and closes per turn) reusing the same seams, not an edit to `runner.ts`/`pipeline.ts`, both of which stay byte-for-byte.
